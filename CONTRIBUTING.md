# Contributing

Thanks for taking the time to improve YouTube Plus. It is a small vanilla
JavaScript userscript, so contributions should stay focused and easy to
verify.

The project is not affiliated with YouTube or Google. Do not propose features
that bypass YouTube restrictions, block ads, download videos or collect user
data.

By contributing you agree that your work is licensed under the project's
[MIT licence](LICENSE).

## Before you start

1. Read [AGENTS.md](AGENTS.md) — repository conventions and the task workflow —
   along with [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) and
   [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).
2. Check [TODO.md](TODO.md). For a non-trivial change, open an issue or pick an
   existing task and agree on the approach before writing code.
3. Write a plan first: the files to change, ordered steps, tests, verification,
   risks and out-of-scope work. Do not start editing until the plan is clear.

## Requirements

- Node.js `>= 20` (`.nvmrc` pins 22 for CI)
- A userscript manager for live testing: [Tampermonkey](https://www.tampermonkey.net/),
  [Violentmonkey](https://violentmonkey.github.io/) or
  [ScriptCat](https://scriptcat.org/)

## Setup

```bash
npm install
npm test             # node:test unit tests
npm run dev          # Vite serve; install the generated dev script (prefix "dev:")
npm run build        # production bundle → dist/ + copied to the repository root
npm run ci           # i18n check + build + artifact verification
```

The git-ignored `dev/harness/` serves a mock YouTube page and the built
userscript, so interface and layout rules can be checked without live YouTube:

```bash
npm run build
node dev/harness/serve.mjs   # http://localhost:5179
```

The manual checklist is in
[docs/DEVELOPMENT.md](docs/DEVELOPMENT.md#local-harness).

## Conventions

- Vanilla ES modules only: no frameworks, no TypeScript, no new runtime
  dependencies without a clear reason.
- GM APIs come from `$` (`vite-plugin-monkey/dist/client`). Do not widen
  `@grant` or `@connect` without a feature that needs it.
- Prefix our DOM nodes and storage with `yp-` / `data-yp-` / `yp_`; create UI
  through `el()`.
- Every setting belongs to a feature schema (`core/schema.js`); never read or
  write `GM_getValue` directly.
- YouTube-specific selectors live in `src/core/constants.js` (`SEL`) or at the
  top of the module that needs them. Prefer element names, `aria-label` and
  `title` over generated classes.
- Never interpolate raw user input into CSS. Custom selectors must pass
  `sanitizeSelector` (`features/interface/custom.js`).
- Use the color tokens in `src/styles/tokens.css` so the UI works in YouTube's
  light and dark themes.
- Errors use a stable `YP-####` code from `core/debug.js`.

## Making a change

- Add or update unit tests for pure logic (`npm test`). Check DOM and YouTube
  behaviour with the harness and, for selector changes, on live YouTube.
- Add every new user-facing string to all eight locales; `npm run check:i18n`
  fails on a missing key.
- Never hand-edit `youtube-plus.user.js` or `youtube-plus.meta.js`; they are
  generated by `npm run build` and committed.
- Update `README.md` and `CHANGELOG.md` when the change is user-visible, and
  `docs/ARCHITECTURE.md` when the structure changes.
- Keep one logical change per pull request. Do not mix refactors with features
  or fixes.

## Commits and pull requests

Follow [Conventional Commits](https://www.conventionalcommits.org/):
`type(scope): subject`, where `type` is one of `feat`, `fix`, `docs`, `style`,
`refactor`, `perf`, `test`, `build`, `ci`, `chore` or `revert`; the scope is
optional and lowercase; the subject is imperative, lowercase and has no
trailing period. Write the message from the actual diff.

Do not add `Co-Authored-By` trailers or "Generated with …" lines.

Before opening a pull request:

1. Run `npm test && npm run ci`.
2. Rebuild the committed artifacts (`npm run build`) if source changed.
3. Describe the change, its motivation, the tests run and any manual checks;
   link the related issue or task.

CI runs the unit tests, the i18n check, the build and artifact verification.
Pull requests should pass it before review.

## Review and releases

Maintainers review for correctness, scope and adherence to the conventions
above; expect questions and requested changes. Releases (version bump,
changelog, rebuilt artifacts) are done by maintainers — do not bump the
version in a feature pull request.

Be respectful in issues, reviews and discussions. Harassment, discrimination
and personal attacks are not tolerated.

## Security

Do not report security issues in a public issue or pull request. See
[SECURITY.md](SECURITY.md) for the private reporting channel and scope.
